## September 2026

### 17 Sep 2026: Panel APIs are direct imports (WP4d)

**Panel APIs are direct imports of function declarations (WP4d, lp-panel first).** `cp.js` and fourteen other files import `setLpMode`, `persistDockedPanel`, `paintLpActiveControl` … from `lp-panel.js`; lp-panel's thirteen registry lines are gone. The cycle `cp.js ↔ lp-panel.js` is safe because only *function declarations* cross it (ESM initialises those before any module body runs) and nothing calls across it at module top level. Two rules keep it safe: a panel's shared constants live in `lib/ids.js`, never imported from a panel or from `cp.js`; and no top-level statement in any module may call into another module. focus-panel followed in WP4e (28 functions, eight of them still on the registry for lite-sections.js until WP6). Next: section-library, globals-panel, inline-edit. The step is scripted: the codemod lists a panel's read functions, rewrites every `sve.fn` into an import, drops dead registry lines and unread live properties, and keeps a compat line only where a standalone script reads the name. One panel per release, proven with `SVE_WORKTREE=1 npm run test:browser` — and check that `npm run cp:build` actually succeeded before trusting that run: a failed build leaves the previous dist on disk.

### 17 Sep 2026: The working-tree proof is only honest when entries are served by stem

**The working-tree proof is only honest when entries are served by stem, on both routes.** The CP loads from `/vendor/visual-editor/build/…`; the preview document loads `bridge.js` from the addon's own route, `/!/sve/build/…`. The first version of the harness intercepted only the CP route, so v1.1.156's split bridge was "proven" against the installed bridge and shipped with a boot-time TDZ. Both routes are intercepted now; a passing run must show the bridge's messages (`bridge sent [hover… click]`), not `[]`.

### 17 Sep 2026: Test baseline (the full paragraph)

**Test baseline:** the PHP suite is green (1,124 tests on 12 Nov 2026, Statamic 6.35.1 / Laravel 13.34, the site's versions). *History, 17 Sep 2026:* 15 PHP tests failed before any V2 work (SveDefaults props_ rename, ComponentProps, StripVisualIds, InjectBridgeScript), and the browser smoke test's "code dock" step was timing-sensitive on v1.1.139 and v1.1.140.

### 18 Sep 2026: The working-tree harness serves one module URL per entry

**The working-tree harness serves one module URL per entry and the standalone scripts too.** Lazy chunks import the entry by *its* hashed name (`./addon-<hash>.js`); the CP's HTML names the *installed* hash. Served as-is, the browser would load the entry twice under two URLs — two copies of the editor's state — so `tests/browser/serve-worktree.mjs` rewrites this checkout's entry names to the installed ones in every body it serves, maps only the installed entry names by stem (any other `addon-*.js` request is served as itself, as production would), answers `/vendor/visual-editor/js/*.js` from `resources/js`, and 404s anything the checkout does not have rather than falling through to the installed copy. The smoke test's last step asserts that every build file the browser loaded is one the manifest names — that step is what caught the next paragraph's bug.

### 18 Sep 2026: Side scripts live in resources/js/side (WP6a/b)

**Side scripts live in `resources/js/side/` (WP6a/b).** Fourteen former standalone scripts are imported, verbatim IIFEs with their own run-once guards, by `side/index.js` — the first import in `addon.js`, in the order their script tags used to run. Two stay in `ServiceProvider::$scripts`: `dedupe-cp-fetch.js`, because Iconify's fieldtype captures `fetch` into a module variable when its own bundle evaluates (measured in its build: `let K = fetch`), so the patch must be in place before any module runs — only a classic script is; and `save-errors.js`. `dock-instant-preview.js` was the third until 3 Nov 2026 (see Instant HTML paint, removed). `disable-publish-stack-pin.js` was deleted in WP6c: the observer it neutralised lived in an old addon.js and exists in no build any more. `section-meta-prefetch.js` is a real module since WP6b-2a: it imports `fetchSetMeta` / `fetchNestedSetMeta` from the section library and is imported by `addon.js` right after it (not through `side/index.js` — pulling the library into the first import would change the module graph's evaluation order). Its `window.fetch` patch and its own URL-keyed JSON cache are gone; the library's `sectionMetaCache` is the one cache, and `invalidateFieldCaches` drops from it by import. The smoke test proves the prefetch: hovering a library card must issue `/!/sve/section-meta?…`. `lite-sections.js` is a real module since WP6b-2b, imported by `addon.js` right after `focus-panel.js`: it imports `isolateSoloSection`, `soloSectionSettingsNow`, `paintFocusHeader`, `focusRowMeta`, `focusBack`, `ensureFocusHeader` from the focus panel, and the focus panel reaches it only through the bus — `soloSection` / `soloSectionSettings` `ask('lite:solo' | 'lite:solo-settings', …)` before isolating (lite mounts the row first and answers true when it hosts the list), and `paintFocusHeader` emits `focus-header:painted` (lite stamps its "load all fields" button on it). No wrapper is put around any function at runtime any more; every caller of `soloSection`, including the ones WP4 turned into direct imports, gets the mount-first behaviour V1 had. html-tree.js and section-fields.js import `openLiteSection` / `refreshLiteSetFields` from it. The smoke test asserts `data-sve-lite=on` after the preview click. The side scripts import their helpers from `lib/` since WP6b-3 (`t`, `csrfToken`, `injectStyle`, `featureOn`, `collectionPresets`, `collectionTemplatesCollection`, and `bpBase` from breakpoints.js) — no file in `side/` defines its own `t()`, reads `$config` or creates a `<style>` tag by hand. Their bodies are still the IIFEs they were (4-space indented, `var`), which is deliberate: verbatim first, formatting later. None of them keeps a run-once flag on `window` any more: a module runs once. Each calls `mark('<name>')` from `lib/debug.js`, which records into `window.__sveDebug.ran` **only if** the page created that object before boot — the browser tests do (`evaluateOnNewDocument`); a real CP page never has it. That is the one sanctioned test hook; `grep window.__sve` must otherwise only hit the kernel (`__sveFeatures`/`__sveStrings` are PHP's handoff to the bridge). Do not add new standalone scripts.

### 18 Sep 2026: The smoke test starts from a fixed layout

**The smoke test starts from a fixed layout and clicks like a person.** The editor hydrates docks, device and zoom from the user's `sve_chrome` preferences on the server and writes them back on every run; the test resets that block on the test account before and after each run (`SVE_PREFS='{…}'` seeds a layout to test). It waits for the preview DOM to settle, aims at an *uncovered* text field (scrolling it into view), waits until the point is hit-testable — while the overlay host's View Transition (`html.sve-morphing`, ~400 ms) runs, every click lands on `<html>` — and asserts a `click` message reached the CP. The preview's viewport varies between runs (docks open or not at boot); the test reports it. `SVE_DEBUG=1` prints which frame received the mouse and what the overlay had at the point.

### 18 Sep 2026: WP7a, bootAddon() is a table of contents

**PHP: `bootAddon()` is a table of contents (WP7a).** What used to be 458 lines in `ServiceProvider::bootAddon()` lives in `src/Boot/`, one class per job, each with a static `register()` and the code moved verbatim: `LivePreviewConfig` (request plumbing, preview config; `devices()` runs after the translations are loaded — the order in bootAddon is not tidiness), `ControlPanelScript` (everything `Statamic::provideToScript` tells addon.js, plus `strings()`), `StoreCollections` (the editor's own collections in the nav, template previews), `Routes` (every `/!/sve/…` route), `Utilities` (the Utility pages and who sees them). The provider keeps only what a provider must do. A Boot class in the `Boot\` namespace must `use` the root-namespace classes it calls (`Stores`, `SetMeta`, …) — the provider got them for free, a moved block does not; every one of the 511 tests errored at boot until they were added.

### 18 Sep 2026: WP7b, Tags\VisualEdit resolves through Tags\Resolve

**PHP: `Tags\VisualEdit` resolves through `Tags\Resolve\*` (WP7b).** The tag keeps `index()` and the attribute builders; the lookups moved out verbatim: `BlueprintFields` (fields by handle, set and replicator config, the type chain — pure, static, with the `$fieldsByHandle` cache), `Icons` and `Placeholders` (pure, static), `Controls` and `BardConfig` (need the tag's params and context: `new Controls($this->params, $this->context)->resolve(…)`), and the trait `ResolvesScope` (section type, set chain, field type — the "where are we" every resolver and the tag share; each has `$this->params`/`$this->context`). Two traps a mechanical move must check for, because the tag's `catch (\Throwable)` blocks turn them into silently empty attributes rather than errors: a moved method that reads a *static property* or a constant declared on the old class (`self::$fieldsByHandle` — declare it where the method now lives), and a class in the root namespace used without `use` (fine in the provider, not in `Boot\` or `Tags\Resolve\`). The 65 VisualEdit tests are the proof; run them before trusting a move.

### 18 Sep 2026: WP7c, the tag is 199 lines

**WP7c: the tag is 199 lines; nothing in `Boot/` or `Tags/Resolve/` is over 315.** `Tags\VisualEdit` keeps `index()` and builds its attributes through `Resolve\Attributes` (the `data-sid-*` core for sets and fields) and `Resolve\SetAttributes` (insert control, outline, grid, global-edit, row template — composes `Attributes`); the remaining lookups are traits it and the resolvers share: `ResolvesScope`, `ResolvesFields` (field match, labels), `ResolvesIcons`, `ResolvesInserts` (replicator config + its cache). `Boot\Routes` is a table of contents for `PreviewRoutes`, `DockRoutes`, `EditorRoutes`; `Boot\ControlPanelScript` asks `ScriptCollections` and `ScriptChrome`; `Resolve\ReplicatorLookups` holds the two recursive set/replicator walks. One more trap for a mechanical move: a helper introduced into `index()` must not reuse a local name the method already has (`$sets` was the list of sets — the tests said "call to a member function on array"). Still over 300 lines: 26 domain classes (`SectionTemplate`, `FileManager`, `DataVars`, `SetPreviewGenerator`, …) — WP7d, one at a time, tests first.

### 18 Sep 2026: WP9b-1, the performance panel's Server tab

**WP9b-1: the performance panel has a Server tab.** `RenderProfile::run($url)` renders the entry behind a URL twice in-process (`Entry::toResponse`, warm then measured) with `RenderProfile\TimedEngine` wrapped around Statamic's Antlers engine (registered under the engine name `antlers`, not the extension) and a `Ledger` that books each template's inclusive and exclusive time; `summarize()` turns it into total / sections / layout and the top templates (rows under 1 % dropped). ### 19 Sep 2026: WP9b-1b, a field is augmented once per request

**WP9b-1b: a field is augmented once per request, not once per read.** Statamic's `Value::value()` has no memory; every `{{ field }}` in every partial augments the raw value again. On the test page that was 2,288 augmentations in one render (310 of 750 ms): 702 of our `responsive` field (each read rebuilt all three breakpoints), 252 of the replicator (`{{ blocks }}` written three times = three augmentations of the rows). `Fieldtypes/MemoizesAugmentation` remembers the answer in `Blink::store('sve-augment')` for the rest of the request, keyed on fieldtype class, field handle, config hash (once per Field object via a WeakMap — a replicator's config is the whole set tree), parent entry id, shallow/deep and the raw value; `ResponsiveFieldtype::performAugmentation` and the addon's `Replicator::augment/shallowAugment` use it. Nothing survives the request, so Live Preview always sees fresh values. Tests in `tests/Fieldtypes/MemoizedAugmentationTest.php`. The theme's other half of the cost — reading `flex_direction.laptop…` in twelve small partials — is the designer's to change (read the field once per partial); the Server tab shows the before and after.

### 19 Sep 2026: WP9b-2, sve_cache and the Editor tab

**WP9b-2: `{{ sve_cache }}` and the Editor tab.** `Tags/SveCache` renders a partial once and remembers it (Laravel cache, 30 days) until one of the named globals is saved: `{{ sve_cache src="cms_styles/layout_style_push" globals="theme_settings" }}` replaces `{{ partial:… }}` in the site's layout. The key is the tag version, site, view file mtime, a hash of each named global's saved data and an optional `key` param — page data is *not* in it, by contract: wrap only what depends on the named globals. What the partial pushed into `style_push` / `script_push` is captured (`StylePushStack::mark()/since()`, `ScriptPushStack` — guards that never autoload the style-push classes when the addon is absent) and replayed on a hit. Off when `statamic-visual-editor.cache.partials` is false, or in a Live Preview carrying unsaved globals (`sve_globals=1`). Trap, met on the first release: the push stacks hold `AntlersString` objects (what `$this->parse()` returns in Statamic 6), which carry closures — `Cache::put` threw "Serialization of 'Closure'" and every page was an error page until the layout was reverted. `since()` casts to string; the addon's tests cannot see it because style-push is not a dev dependency, so the site's curl before/after check is the proof. Statamic's `{{ cache }}` was not used: it disables itself in Live Preview, where the saving matters most. The Editor tab (`cp/perf/editor-vitals.js`, sampled once a second only while the tab is open) reads the CP window itself, no kernel: long tasks via PerformanceObserver, bridge messages per second off the window's `message` events (`source === SOURCE`), and keystroke → preview from `input` on the CP document to `statamic:preview-updated` on the preview window (the event preview.js dispatches after a morph; the listener follows the iframe across reloads). Budgets in `report.js`; pure helpers unit-tested in `tests/js/editor-vitals.test.js`; `npm run test:perf` opens both tabs.

### 19 Sep 2026: The suite is green; the 15 known failures were outdated tests

**The suite is green; the 15 "known failures" were outdated tests, not bugs.** Four groups, each a decision the code had taken that the test never followed: `SveDefaultsTest` and `ComponentPropsTest` still expected a `props` array plus bare names, while every prop is written and read as `props_<handle>` (`ComponentProps::PREFIX` — the site's own components say `{{ props_headline }}`); `StripVisualIdsTest` expected grid rows to lose `_visual_id`, while `StripVisualIds::processGridItems()` keeps it on purpose (a grid row is not regenerated on CP load and Live Preview needs a stable id in the loop — replicator rows inside the grid still lose theirs); `InjectBridgeScriptTest` overrode a hook that no longer exists (`resolveBridgeUrl` → `resolveScriptUrl($entry)`, one per built entry). When a test fails after a deliberate change, the test moves with the decision and says why. Also fixed: `syncComponentMap` asked the server for the file behind `{{ partial src="blocks/{type}" }}` on every dock open — a tokenised name is a folder (`hasToken()` in `dock-partials.js`, shared with the tree's row menu); the server lists it, nobody fetches it as a file.

### 26 Sep 2026: The Theme panel's Fonts tab

**The Theme panel's Fonts tab (26 September 2026).** One list of the site's fonts: `public/fonts/fonts.css` (config `fonts.root` / `fonts.url`), an `@font-face` per file and an `@import` per Adobe Fonts kit; the site's `{{ theme_tokens }}` links it with its mtime, so a font added on the server needs no build. `src/Fonts/` — `Folder` (paths; `store()` never overwrites other bytes, it takes `-2`), `Stylesheet` (reads the rules back, only ever *adds*: after the family's last face or at the end, a kit after the last import), `GoogleFonts` (catalog = Google's own metadata, trimmed, cached a week; files from css2 asked as a current Chrome, so WOFF2; a family with a `wght` axis is asked for its whole range — Google serves the same variable file for every weight anyway), `Uploads` (format from the first bytes), `AdobeKits`, `Listing`. Routes `/!/sve/fonts*` in `EditorRoutes`, gated by `site_css` like the panel; every write answers with the new listing, commits via `GitSync` (which now includes the fonts folder) and flushes the static cache. JS: `cp/theme-panel/fonts.js` (store + server), `font-helpers.js` (pure), `google-fonts.js` (catalog, `text=` previews under `sve-gf-*` aliases), `font-files.js` (reads name/OS/2/fvar in the browser; `woff2-encoder` — Google's encoder as wasm — is a lazy 1 MB chunk loaded only to convert, its 295 KB decoder only to read a WOFF2). Installed families are drawn in the CP under `sve-font-*` aliases, never their own names (a site "Inter" must not restyle the CP). Nothing deletes a font yet — deliberate. Tests: `FontsTest`, `FontsControllerTest`, `tests/js/fonts.test.js`, `npm run test:fonts` (needs the installed PHP; puts fonts.css back and removes only the paths the run added).

### 12 Oct 2026: Live reload on the public site

**Live reload on the public site (12 October 2026).** For a developer who edits the site's files on the server — VS Code over SSH, Site Files, the dock — and keeps the public page open beside it, the way `npm run dev` reloads it on a laptop. `features.live_reload` (off by default) + `live_reload_access` (`ToolbarAccess`, super by default). `Http/Middleware/InjectLiveReload` sits in the `web` group next to `InjectEditButton` and for the same reason — it wraps Statamic's static-cache middleware, so the button never reaches the cache; not in Live Preview, not on a `sve_perf` reading, not while `public/hot` exists (Vite reloads then). ### The selection panel (phase 0, 19 October 2026, behind `selection_panel`)

The left column's successor to the focus panel. The focus panel isolates
Statamic's whole publish form down to one row with marks on the form's DOM
(`solo`), waits for lite to mount the row, and shows a second time when the
block inside had not opened — seven routes wrote into that column and the
state lived in two places (DOM marks and `sveState`), which is what made the
column jump, show the wrong thing after Publish, and vanish when a top-bar
tool opened. The selection panel draws the selected row itself and owns one
fact: which row is selected.

**Files.** `lib/selection.js` (the one selection: `select`, `clearSelection`,
`currentSelection`, `onSelection`), `cp/panel/resolve.js` (pure: a row's id →

1. *`display: none` on the hidden form unmounts it.* Statamic's PublishTabs
   measures its tab bar; at zero width every tab overflows, the bar re-renders,

3. *The lite field remounts while its form stays.* Vue creates the new

### One focus frame (since 24 October 2026)

The header, the footer, a global section and a component are *in focus* the same way: `bridge/focus-frame.js` draws one frame on the element — a 1px outline in the kind's colour (header/footer blue `#60a5fa`, global purple `#7c3aed`, component teal `#0f766e`), a label chip top-left, and top-right `[Not saved] [Save] [Close ✕]`, the first two only while `dirtyable && dirty`. The frame is an absolutely positioned `<div data-sve-focus-frame="{kind}" data-sve-ui>` hung off `<html>` (it survives the morph), placed from `getBoundingClientRect()` + scroll and re-placed on resize/scroll/ResizeObserver; `pointer-events: none` except the chips, which stop their own pointerdown/click so `sid-targets` never reads them as a click on the page (`focusFrameOwns`). `mountFocusFrame` is idempotent per kind (re-points `el`, updates label/dirty/callbacks), `unmountFocusFrame(kind)`, `setFocusFrameDirty`, `setFocusFrameLabel`, `focusFrameOpen(kind)`. The three modules keep their data and their enter paths; they only hand the frame its element and two callbacks: `header-footer.js` (`mountChromeFrame`, Save → `SAVE_CHROME`, Close → `requestCloseChrome`), `global-sections.js` (`mountGlobalFrame`, Save → `SAVE_GLOBAL_SECTION`, Close → `requestCloseGlobal`), `component-pick.js` (frame on the first instance, Close → `requestCloseComponent` → `REQUEST_CLOSE_COMPONENT` → `dock:exit-component`; a component is a file saved on the way out, so no dirty state). Gone with it: the chrome corner chip and bottom bar (`mountChromeClose`, `mountChromeBar`, `chromeBarOff`), the global bottom bar (`mountGlobalBar`, `sveFocusBarStyle`, `GLOBAL_BAR_ID`, `alongBandBottom`) and their lang keys (`chrome_bar*`, `global_bar*`). What changed in behaviour, on purpose: a click outside a focused global section asks to close it (as header/footer and component already did); Escape leaves the innermost focus — component frame first, then header/footer, then global — gated on `focusFrameOpen('component')`, *not* `bridgeState.componentFocus`, because the dock holds the header's own file as a `view:` too and that flag is set while the header is edited with no instance marked; the global close dialog offers Save, like the chrome one; `dock:exit-component` takes any partial the preview focuses (`componentSrcFromType`), not only `partials/components/*` — the tree's and the props panel's Exit still show for those alone. Hidden while focused: the global badge and the chrome `::before` label (the frame's chip says it). Tests: `tests/js/focus-frame.test.js`; `instant-chrome.mjs` leaves a half through `[data-sve-focus-frame] [data-sve-focus-close]`. Rollback: `v1.1.593` is the last tag before the frame (local tag `pre-focus-frame-2026-10-24`).
